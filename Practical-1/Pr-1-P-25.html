Integrated Algorithm — From Specification to Tested Solution

This period brings together the practical skills developed so far. Students receive a small problem specification, identify inputs and outputs, decompose the task into subroutines, validate data, process an array and test the finished solution.

Core idea: Strong programmers do not jump straight into code. They understand the requirement, plan the solution, build it in manageable parts and test each important condition.

3 · Example #1 — Validation subroutine

FUNCTION ValidMark(Mark)
  RETURN Mark >= 0 AND Mark <= 100
ENDFUNCTION

Once this function exists, the input section can repeatedly request a new mark until ValidMark(Mark) is TRUE.

27–35 min · Worked design

4 · Example #2 — Average subroutine

FUNCTION Average(A, Count)
  Total ← 0
  FOR I ← 1 TO Count
    Total ← Total + A[I]
  NEXT I
  RETURN Total ÷ Count
ENDFUNCTION
The function assumes that Count is valid. That responsibility belongs to the calling algorithm, which should validate the number of values before using it.
35–42 min · Integrated example

5 · Example #3 — Main algorithm structure

CONSTANT N ← 10
DECLARE Marks : ARRAY[1:N] OF INTEGER

FOR I ← 1 TO N
  INPUT Marks[I]
  WHILE Marks[I] < 0 OR Marks[I] > 100 DO
    OUTPUT "Enter 0 to 100"
    INPUT Marks[I]
  ENDWHILE
NEXT I

Avg ← Average(Marks, N)
High ← Maximum(Marks, N)
OUTPUT Avg
OUTPUT High
42–47 min · Guided workout

6 · Build a test plan

For the integrated mark system, choose tests that check normal marks, the 0/100 boundaries, invalid values and the pass boundary at 50.
Useful values: 65 (normal), 0 and 100 (range boundaries), -1 and 101 (invalid), 49 and 50 (pass boundary). A larger test set can also include 51 and a mixture of several marks.

5 · Worked Example — Pass counter

FUNCTION CountPasses(A, Count)
  Passes ← 0
  FOR I ← 1 TO Count
    IF A[I] >= 50 THEN
      Passes ← Passes + 1
    ENDIF
  NEXT I
  RETURN Passes
ENDFUNCTION

This is a focused module: it receives the array and number of elements and returns one result.

6 · Workout — Write the complete solution

8 · Debugging workout

FUNCTION CountPasses(A, Count)
  Passes ← 1
  FOR I ← 1 TO Count
    IF A[I] >= 50 THEN
      Passes ← Passes + 1
    ENDIF
  NEXT I
  RETURN Passes
ENDFUNCTION

What is the likely fault?

The counter should begin at 0, not 1. Starting at 1 adds an extra pass to every result.

10 · Challenge — Improve the design

Suggest one reason why CountPasses is better as a separate function than placing its entire loop in the main program.
It gives the task one clear responsibility, makes the main program easier to read, allows the function to be tested independently and makes the calculation reusable.

13 · Mini exam question

Explain two benefits of decomposing a programming problem into subroutines.

Any two: simpler main program/readability; individual modules can be tested and debugged separately; code can be reused; each module has a clear responsibility; changes can be made to one part with less impact on others.

14 · Final practical challenge

Create your own small program using at least one array, one loop, one validation check, one function and one systematic test table. Before coding, write the specification in one paragraph.
  1. State the problem.
  2. List inputs and outputs.
  3. Identify the data structure.
  4. Choose subroutines.
  5. Add validation.
  6. Write the algorithm.
  7. Test normal, boundary and invalid cases.
  8. Debug and refine.

15 · Common mistakes

  • Coding before understanding the specification.
  • Putting every task into one huge algorithm.
  • Forgetting to initialise counters and accumulators.
  • Validating some inputs but not others.
  • Testing only one successful case.
  • Changing working code without first identifying the fault.
  • Failing to test module outputs independently.

16 · Self-assessment

Can you take a programming specification, decompose it, build a modular solution, validate inputs and test the finished algorithm systematically?
