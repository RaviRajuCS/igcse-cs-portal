Testing Algorithms Systematically

Students now learn to test their completed algorithms deliberately rather than simply trying one input and assuming the program works. The focus is on normal, boundary and invalid test data, expected results, trace tables and using test evidence to find faults.

Core idea: Good testing does not prove that a program has no errors. It provides evidence that important conditions and edge cases have been checked.

1 · Why test more than once?

A program accepts marks from 0 to 100. A teacher tests only 75 and it works. Can the teacher conclude the validation is correct?
No. Values such as 0, 100, -1 and 101 may expose boundary or validation errors.

7 · Worked Example #3 — Fault finding

IF Mark > 50 THEN
  OUTPUT "Pass"
ELSE
  OUTPUT "Fail"
ENDIF

Requirement: 50 or more is a pass. What happens with input 50?

The algorithm outputs Fail, but the requirement says 50 should pass. The condition should be Mark >= 50.

8 · Debugging workout

A program works for 25 and 75 but fails for 0 and 100. What should you investigate first?
Investigate the boundary conditions and comparison operators. The program may be using > or < where >= or <= is required.

10 · Challenge — Minimal but effective tests

A mark is classified as Fail (0–49), Pass (50–79) or Distinction (80–100). Suggest a compact test set that exercises all categories and important boundaries.
Suggested tests: 0, 49, 50, 79, 80, 100, plus an invalid value such as -1 or 101. These exercise the lower/upper boundaries of each category and invalid data.

11 · Think like an examiner

Why is 49 useful when testing the Fail/Pass boundary at 50?

12 · Mini exam question

An algorithm accepts a whole number from 1 to 20 inclusive. Give one normal, two boundary and two invalid test values.

Normal: 10. Boundary: 1, 20. Invalid: 0, 21.

13 · Common mistakes

  • Testing only normal values.
  • Forgetting values immediately outside a boundary.
  • Not predicting the expected result first.
  • Confusing boundary data with invalid data.
  • Reading a trace table without tracking variable changes.
  • Assuming one successful test proves the algorithm is correct.

14 · Self-assessment

Can you design effective test data, predict results, trace algorithms and use failed tests to identify likely faults?
