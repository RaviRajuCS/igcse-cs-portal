Input Validation and Defensive Programming

Students now strengthen their programs by making them safe and reliable. Instead of assuming that users always enter correct data, students design validation checks, identify boundary values and prevent invalid data from entering the main algorithm.

Core idea: Validate input before using it. A robust algorithm considers normal values, boundary values and invalid values.

1 · Why validate?

A program asks for a mark from 0 to 100. A student enters 175. Should the program immediately calculate with that value?
No. The value is outside the permitted range and should be rejected or requested again.

2 · Range validation

INPUT Mark
WHILE Mark < 0 OR Mark > 100 DO
  OUTPUT "Invalid mark"
  INPUT Mark
ENDWHILE
OUTPUT "Accepted"

The loop continues until the input satisfies the permitted range.

4 · Example #1 — Valid age

INPUT Age
WHILE Age < 5 OR Age > 18 DO
  OUTPUT "Enter an age from 5 to 18"
  INPUT Age
ENDWHILE
OUTPUT "Valid age"

The accepted boundary values are 5 and 18.

This pattern is reusable for menus, option numbers and controlled selections.

6 · Workout — Password length

A password must contain at least 8 characters. Keep asking until the user enters a password of length 8 or more.
INPUT Password
WHILE LENGTH(Password) < 8 DO
  OUTPUT "Password too short"
  INPUT Password
ENDWHILE
OUTPUT "Accepted"

7 · Worked Example #3 — Validation + processing

INPUT Mark
WHILE Mark < 0 OR Mark > 100 DO
  OUTPUT "Invalid"
  INPUT Mark
ENDWHILE

IF Mark >= 50 THEN
  OUTPUT "Pass"
ELSE
  OUTPUT "Fail"
ENDIF

Notice the order: validate first, process second.

8 · Debugging workout

INPUT Mark
WHILE Mark > 0 AND Mark < 100 DO
  OUTPUT "Invalid"
  INPUT Mark
ENDWHILE

The required range is 0 to 100 inclusive. What is wrong with the condition?

The condition identifies the valid middle values rather than the invalid values. For inclusive 0–100 validation, the invalid condition is Mark < 0 OR Mark > 100.

13 · Common mistakes

  • Rejecting valid boundary values by using <= or >= incorrectly.
  • Using AND instead of OR for an invalid range condition.
  • Processing data before validating it.
  • Forgetting to request new input inside the validation loop.
  • Testing only normal values and ignoring boundaries.
  • Confusing an inclusive range with an exclusive range.
