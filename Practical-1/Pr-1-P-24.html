Robust Algorithms and Error Handling

Students now extend input validation into broader defensive programming. The goal is to anticipate what can go wrong, detect problems early and design a sensible response rather than allowing incorrect data to corrupt the rest of the solution.

Core idea: A robust program does not merely work with good input. It recognises foreseeable problems and responds appropriately.

0–8 min · Retrieval

1 · Validation versus ordinary processing

If a program expects a menu choice from 1 to 4, what should happen when the user enters 9?
The program should detect the invalid value, give a useful response and request another value instead of processing 9 as a valid choice.
8–18 min · Teach

2 · Separate validation from processing

INPUT Mark
WHILE Mark < 0 OR Mark > 100 DO
  OUTPUT "Invalid mark"
  INPUT Mark
ENDWHILE

IF Mark >= 50 THEN
  OUTPUT "Pass"
ELSE
  OUTPUT "Fail"
ENDIF

Keeping validation first makes the main processing section easier to read, test and maintain.

18–27 min · Teach

3 · Defensive checks before risky operations

INPUT Count
WHILE Count <= 0 DO
  OUTPUT "Enter a positive count"
  INPUT Count
ENDWHILE
Total ← 0
FOR I ← 1 TO Count
  INPUT Value
  Total ← Total + Value
NEXT I
Average ← Total ÷ Count
OUTPUT Average

The validation prevents a zero count from reaching the division operation.

27–35 min · Worked example

4 · Example #1 — Prevent division by zero

INPUT NumberOfValues
WHILE NumberOfValues < 1 DO
  OUTPUT "At least one value is required"
  INPUT NumberOfValues
ENDWHILE
Total ← 0
FOR I ← 1 TO NumberOfValues
  INPUT Value
  Total ← Total + Value
NEXT I
OUTPUT Total ÷ NumberOfValues
The important design decision is not simply calculating an average—it is making sure the divisor can never be zero.

5 · Example #2 — Safe array position

  OUTPUT "Invalid position"
  INPUT Position
ENDWHILE
OUTPUT Scores[Position]

The validation protects the array access by restricting the index to the permitted range.

42–47 min · Guided workout

6 · Defensive programming workout

A program asks for the number of students and then calculates an average. What input condition should be rejected before the calculation?
Zero or a negative number of students. A count must be at least 1 if the program is going to calculate an average using that count as a divisor.

8 · Debugging workout

INPUT Index
IF Index >= 1 THEN
  OUTPUT A[Index]
ENDIF

The array has only 10 elements. What important validation is missing?

The upper boundary is missing. The condition should also ensure Index <= 10. Otherwise a value such as 50 could still cause an invalid array access.

10 · Challenge — Robust average with valid data

Input a positive number of marks, then accept only marks from 0 to 100 and calculate their average.
INPUT Count
WHILE Count < 1 DO
  OUTPUT "Enter at least 1"
  INPUT Count
ENDWHILE
Total ← 0
FOR I ← 1 TO Count
  INPUT Mark
  WHILE Mark < 0 OR Mark > 100 DO
    OUTPUT "Enter 0 to 100"
    INPUT Mark
  ENDWHILE
  Total ← Total + Mark
NEXT I
Average ← Total ÷ Count
OUTPUT Average

13 · Common mistakes

  • Checking only one side of a range.
  • Validating after the risky operation instead of before it.
  • Allowing zero when it will be used as a divisor.
  • Forgetting the upper array boundary.
  • Giving vague error messages.
  • Failing to request corrected input after rejection.
