Loops That Depend on a Condition

Students now move beyond fixed-count loops. Sometimes we do not know how many repetitions are needed. The algorithm must continue while a condition remains true, or repeat until a required condition becomes true.

Core distinction: FOR is ideal when the repetition count is known. WHILE and REPEAT…UNTIL are useful when repetition depends on a condition.

1 · Which loop?

A program must input a password repeatedly until the user enters the correct password. Do we know the number of attempts in advance?
No. A condition-controlled loop is appropriate because the number of attempts is unknown.
8–18 min · Teach

2 · WHILE…ENDWHILE

WHILE Number <= 100 DO
  INPUT Number
ENDWHILE

A WHILE loop checks its condition before executing the body. If the condition is false initially, the body may execute zero times.

Teaching warning: Make sure something inside the loop can eventually make the condition false, otherwise an infinite loop can occur.
18–27 min · Teach

3 · REPEAT…UNTIL

REPEAT
  INPUT Number
UNTIL Number > 0

REPEAT…UNTIL checks the condition after the body. Therefore the body executes at least once.

27–35 min · Worked example

4 · Example #1 — Password validation

REPEAT
  INPUT Password
UNTIL Password = "CAMBRIDGE"
OUTPUT "Access granted"

The user must provide at least one password attempt. The loop ends only when the required value is entered.

35–42 min · Worked example

5 · Example #2 — Input validation

Input a mark and keep asking until the mark is between 0 and 100.
REPEAT
  INPUT Mark
UNTIL Mark >= 0 AND Mark <= 100
OUTPUT Mark

Total ← 0
INPUT Number
WHILE Number <> 0 DO

  INPUT Number
ENDWHILE
OUTPUT Total

9 · Debugging — Infinite loop

Number ← 1
WHILE Number <= 5 DO
  OUTPUT Number
ENDWHILE

What is missing?

The loop variable never changes, so Number remains 1 and the condition stays TRUE. Add an update such as Number ← Number + 1.

Write an algorithm that repeatedly inputs a number until a number between 1 and 10 inclusive is entered.

REPEAT

13 · Common mistakes

  • Using WHILE when the body must execute at least once.
  • Forgetting to change the variable controlling a WHILE loop.
  • Using the wrong boundary in validation.
  • Accidentally including a sentinel value in a calculation.
  • Choosing a condition that can never become false.

14 · Self-assessment
